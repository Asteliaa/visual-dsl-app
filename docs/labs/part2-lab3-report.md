## 2 ХОД РАБОТЫ

### 2.1 Обзор предметной области

К предметной области сервиса *DiagramCode* добавлена новая сущность «Пользователь»
(*User*): *email* — уникальный адрес электронной почты, приводится к нижнему регистру перед
сохранением; *passwordHash* — необратимый хеш пароля, сам пароль в открытом виде нигде не
хранится и не логируется; *isActive* — признак активности учётной записи, по умолчанию
*true*; *loginAttempts* — счётчик неудачных попыток входа подряд, по умолчанию 0, используется
для временной блокировки учётной записи. Существующая сущность «Диаграмма» (*Diagram*)
получила новое поле *userId*, связывающее диаграмму с создавшим её пользователем — подробнее
это решение и его обоснование описаны в разделе 2.5.

### 2.2 Теоретические сведения

Хеширование паролей — это одностороннее преобразование пароля в строку фиксированной длины,
из которой исходный пароль восстановить практически невозможно. В проекте использован пакет
*bcrypt*, включающий соль (*salt*) в сам хеш, что защищает от атак по заранее вычисленным
таблицам (*rainbow tables*): *bcrypt*.*hash*(*password*, 12) хеширует пароль с параметром
*saltRounds* = 12 (число раундов внутреннего алгоритма *Blowfish*, определяющее
вычислительную стоимость хеширования и, соответственно, стойкость к перебору), а
*bcrypt*.*compare*(*password*, *hash*) сравнивает введённый пароль с сохранённым хешем без
необходимости его расшифровки.

*JWT* (*JSON Web Token*) — компактный самодостаточный токен, состоящий из трёх частей,
разделённых точками: заголовка (*header*, содержит алгоритм подписи), полезной нагрузки
(*payload*, содержит произвольные данные, в проекте — *userId*) и подписи (*signature*),
вычисляемой на основе первых двух частей и секретного ключа сервера. Токен подписывается
методом *jwt*.*sign*({ *userId* }, *JWT_SECRET*, { *expiresIn*: "7*d*" }) и передаётся клиентом
на сервер в заголовке *Authorization*: *Bearer* &lt;*token*&gt; при каждом запросе к защищённым
маршрутам; сервер проверяет подпись методом *jwt*.*verify*(*token*, *JWT_SECRET*), не обращаясь
при этом к базе данных — в этом и состоит его ключевое отличие от серверных сессий, где
состояние входа хранится на сервере (в памяти или в хранилище сессий) и требует обращения к
нему при каждом запросе.

Отдельного внимания заслуживает требование не раскрывать в сообщении об ошибке входа, что
именно неверно — email или пароль. Если возвращать разные сообщения («пользователь не найден»
против «неверный пароль»), злоумышленник может перебором email-адресов установить, какие из
них зарегистрированы в системе (так называемая атака *user enumeration*), даже не пытаясь
подобрать пароль. Поэтому в реализации оба случая — отсутствие пользователя с таким email и
неверный пароль у существующего пользователя — возвращают один и тот же текст ошибки
«Неверные учетные данные» с одним и тем же кодом состояния 401.

### 2.3 Регистрация пользователей

Эндпоинт *POST* /*auth*/*register* принимает *email* и *password* в теле запроса. Перед
обращением к базе данных выполняется последовательная валидация: сначала проверяется, что оба
поля вообще переданы, затем формат email проверяется регулярным выражением, затем пароль
проверяется функцией *validatePassword* на соответствие требованиям сложности — минимум 8
символов, хотя бы одна строчная буква, хотя бы одна заглавная буква, хотя бы одна цифра, хотя
бы один спецсимвол, а также отсутствие пароля в коротком списке заведомо распространённых
паролей (*password1*!, *qwerty*123!, и т.п.). Если хотя бы одно условие не выполнено, сервер
немедленно возвращает 400 *Bad Request* с текстом конкретной нарушенной проверки, не обращаясь
к базе. Отдельно проверяется, что пользователь с таким (приведённым к нижнему регистру) email
ещё не зарегистрирован — при совпадении также возвращается 400. При успешном прохождении всех
проверок пароль хешируется через *bcrypt*.*hash* с *saltRounds* = 12, создаётся запись
пользователя, и клиенту возвращается 201 *Created* с *id* и *email* — хеш пароля в ответе не
передаётся.

### 2.4 Вход и блокировка учётной записи

Эндпоинт *POST* /*auth*/*login* ищет пользователя по приведённому к нижнему регистру *email*.
Если пользователь не найден — возвращается общая ошибка 401 (см. раздел 2.2). Если найден, но
деактивирован (*isActive* = *false*), возвращается отдельный код 403 с сообщением об
деактивации — этот случай не смешивается с общей ошибкой, поскольку не связан с попыткой
подбора учётных данных. Если у пользователя уже накоплено 5 неудачных попыток входа подряд,
дальнейшие попытки отклоняются кодом 423 (*Locked*) без проверки пароля вообще — учётная
запись временно заблокирована. В остальных случаях введённый пароль сравнивается с хешем через
*bcrypt*.*compare*: при несовпадении счётчик *loginAttempts* увеличивается на единицу и клиенту
возвращается общая ошибка 401; при совпадении счётчик сбрасывается в 0, и сервер подписывает и
возвращает *JWT*-токен со сроком действия 7 дней вместе с кодом 200.

### 2.5 Защита маршрутов диаграмм и владение диаграммами

*Middleware* *authenticate* (файл `middleware/auth.js`) читает заголовок *Authorization*,
проверяет наличие схемы *Bearer*, при отсутствии заголовка или неверной схеме сразу возвращает
401. Если заголовок присутствует, токен проверяется через *jwt*.*verify* с тем же секретом,
которым он был подписан; при неудачной проверке (истёкший срок действия, неверная подпись,
повреждённый токен) также возвращается 401. При успешной проверке *userId* из полезной нагрузки
токена кладётся в *req*.*userId*, и запрос передаётся дальше по цепочке *middleware* вызовом
*next*(). Этот *middleware* подключён в `app.js` перед маршрутами /*diagrams*, то есть все пять
операций *CRUD* над диаграммами теперь требуют действительного токена.

объясняется тем, что до этой лабораторной работы у диаграмм не было понятия владельца, а
модель без него не позволяет продемонстрировать разницу между простой проверкой «есть ли
валидный токен» и настоящей авторизацией по ресурсу. Контроллер *diagramController*.*js*
теперь проставляет *userId* = *req*.*userId* при создании диаграммы и добавляет условие *userId*
= *req*.*userId* во все операции чтения, обновления и удаления — так, что пользователь A не
может увидеть, изменить или удалить диаграмму пользователя B даже зная её числовой *id*;
попытка обратиться к чужой диаграмме возвращает 404 *Not Found*, а не 403 *Forbidden*, чтобы не
подтверждать сам факт существования диаграммы с таким *id* у другого пользователя. Это
решение было сознательно выбрано вместо более узкой трактовки задания (только проверка
наличия токена без разделения диаграмм между пользователями), поскольку модель с полем без
единого владельца плохо соответствует смыслу «авторизации» — авторизация подразумевает не
только «кто ты», но и «что тебе можно», а без привязки диаграммы к владельцу второй вопрос не
имеет смысла проверять.

## 3 ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ

1. Зачем хешировать пароли, а не хранить их в открытом виде?
Хранение пароля в открытом виде означает, что при компрометации базы данных (утечке) все
пароли пользователей становятся известны злоумышленнику немедленно и в готовом для
использования виде, в том числе для входа на другие сервисы, где пользователь мог применить
тот же пароль. Хеш — необратимое преобразование, из которого исходный пароль напрямую не
восстановить.

2. Что такое *salt* (соль) и зачем он нужен при хешировании?
Соль — случайная строка, добавляемая к паролю перед хешированием и сохраняемая вместе с
хешем. Она гарантирует, что одинаковые пароли у разных пользователей дают разные хеши, что
делает бесполезными заранее вычисленные таблицы хешей (*rainbow tables*). В *bcrypt* соль
формируется автоматически и встраивается в сам результат *hash*(), поэтому её не нужно хранить
отдельным полем.

3. Что означает параметр *saltRounds* в *bcrypt*.*hash*(*password*, *saltRounds*)?
Это число раундов работы внутреннего алгоритма — каждое увеличение на единицу удваивает
вычислительную стоимость хеширования. Значение 12, использованное в проекте, — общепринятый
баланс между стойкостью к перебору и временем отклика сервера при регистрации/входе.

4. Из каких частей состоит *JWT* и что в них содержится?
Из трёх частей, закодированных в *Base*64 и разделённых точками: заголовок (алгоритм подписи и
тип токена), полезная нагрузка (произвольные данные, в проекте — *userId* и служебные поля
*iat*/*exp*) и подпись, вычисленная на основе первых двух частей и секретного ключа сервера.

5. Почему *JWT* не нужно искать в базе данных при каждой проверке, в отличие от серверных
сессий?
Потому что вся необходимая информация (кто пользователь, когда истекает токен) уже содержится
внутри самого токена, а его подлинность подтверждается криптографической подписью — серверу
достаточно пересчитать подпись тем же секретом и сравнить, не обращаясь к хранилищу. Серверные
сессии, напротив, хранят состояние входа на сервере и требуют обращения к этому хранилищу при
каждом запросе.

6. Что произойдёт, если секретный ключ (*JWT_SECRET*) окажется скомпрометирован?
Злоумышленник сможет подписывать произвольные токены от имени любого пользователя, включая
несуществующих, и они будут проходить проверку *jwt*.*verify* как подлинные. Поэтому секрет
хранится только в переменной окружения, не публикуется в репозитории и должен быть достаточно
длинной случайной строкой.

7. Почему в ответе на неверный email и на неверный пароль при входе возвращается одно и то же
сообщение об ошибке?
Чтобы не дать злоумышленнику возможность перебором email-адресов определить, какие из них
зарегистрированы в системе (атака *user enumeration*), отдельно от попытки подобрать сам
пароль. Подробнее — раздел 2.2.

8. Как реализована блокировка учётной записи после нескольких неудачных попыток входа?
Каждая неудачная попытка увеличивает счётчик *loginAttempts* пользователя на единицу; при
успешном входе счётчик сбрасывается в 0. Если счётчик достиг 5, дальнейшие попытки входа
отклоняются кодом 423 без сравнения пароля вообще, пока счётчик не будет сброшен успешным
входом или административно.

9. Как *middleware* *authenticate* передаёт информацию о текущем пользователе в контроллер?
После успешной проверки токена *middleware* извлекает *userId* из полезной нагрузки токена и
присваивает его свойству *req*.*userId*; поскольку *Express* передаёт один и тот же объект
*req* по всей цепочке *middleware* и обработчиков для одного запроса, контроллер диаграмм
получает доступ к этому значению напрямую через *req*.*userId*.

10. Почему попытка обратиться к чужой диаграмме возвращает 404, а не 403?
Возврат 403 *Forbidden* подтвердил бы, что диаграмма с указанным *id* существует, просто
принадлежит другому пользователю, — то есть раскрыл бы факт её существования постороннему
лицу. Код 404 *Not Found* не различает «диаграммы с таким *id* не существует» и «диаграмма
существует, но не принадлежит текущему пользователю», что безопаснее с точки зрения утечки
информации о чужих данных.

## ПРИЛОЖЕНИЕ А (обязательное). Листинг `controllers/authController.js` и `middleware/auth.js`

```js
// controllers/authController.js
const bcrypt = require("bcrypt");
const jwt = require("jsonwebtoken");
const { ValidationError } = require("sequelize");
const User = require("../models/User");
const { isValidEmail, validatePassword } = require("../utils/validation");

const SALT_ROUNDS = 12;
const MAX_LOGIN_ATTEMPTS = 5;
const GENERIC_LOGIN_ERROR = "Неверные учетные данные";

async function login(req, res, next) {
  try {
    const { email, password } = req.body;
    if (!email || !password) {
      return res.status(400).json({ error: "Требуются email и пароль" });
    }
    const user = await User.findOne({ where: { email: email.toLowerCase() } });
    if (!user) {
      return res.status(401).json({ error: GENERIC_LOGIN_ERROR });
    }
    if (!user.isActive) {
      return res.status(403).json({ error: "Учётная запись деактивирована" });
    }
    if (user.loginAttempts >= MAX_LOGIN_ATTEMPTS) {
      return res.status(423).json({ error: "Аккаунт заблокирован после 5 неудачных попыток входа" });
    }
    const passwordMatches = await bcrypt.compare(password, user.passwordHash);
    if (!passwordMatches) {
      user.loginAttempts += 1;
      await user.save();
      return res.status(401).json({ error: GENERIC_LOGIN_ERROR });
    }
    user.loginAttempts = 0;
    await user.save();
    const token = jwt.sign({ userId: user.id }, process.env.JWT_SECRET, { expiresIn: "7d" });
    res.status(200).json({ token });
  } catch (err) {
    next(err);
  }
}

module.exports = { login };
```

const jwt = require("jsonwebtoken");

function authenticate(req, res, next) {
  const header = req.headers.authorization;
  if (!header || !header.startsWith("Bearer ")) {
    return res.status(401).json({ error: "Отсутствует токен авторизации" });
  }
  const token = header.slice("Bearer ".length);
  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    req.userId = decoded.userId;
    next();
  } catch (err) {
    return res.status(401).json({ error: "Невалидный или просроченный токен" });
  }
}

module.exports = authenticate;
